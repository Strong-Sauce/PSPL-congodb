# BUG-001

## Date

2026-07-24

## Version

Unknown

## Category

Backend / Spring Boot / Spring MVC Routing

## Severity

High

## Status

Resolved

## Detection Method

Runtime Exception (HTTP 500 Internal Server Error)

## Symptoms

Opening a Product Detail page resulted in an HTTP 500 response.

Error:

```text
Ambiguous handler methods mapped for '/products/{id}'
```

Product details could not be retrieved.

---

## Immediate Cause

Spring Boot found two controller methods capable of handling:

```
GET /products/{id}
```

and failed to determine which handler should process the request.

---

## Root Cause

The backend exposed REST APIs under:

```
/products/**
```

while the Angular SPA forwarding controller also matched:

```
/products/{id}
```

The overlapping route mappings created an ambiguity inside Spring MVC.

---

## Investigation Summary

- Reproduced the issue.
- Verified ProductController mappings.
- Reviewed registered Spring MVC handlers.
- Identified conflicting mapping in SpaController.
- Confirmed routing conflict.

---

## Fix Implemented

Introduced a dedicated API namespace.

Backend:

```
/api/products/**
```

Angular updated to consume:

```
http://localhost:8080/api/products
```

This completely separated API endpoints from SPA routing.

---

## Files Changed

- ProductController.java
- SpaController.java
- Angular ProductService
- Angular environment configuration

---

## Verification

Confirmed:

- Product Detail loads successfully.
- No ambiguous mapping exceptions.
- SPA routing continues functioning normally.

---

## Regression Risk

Low

---

## Prevention

- Reserve `/api/**` exclusively for REST endpoints.
- Never allow SPA forwarding routes to overlap API endpoints.
- Maintain consistent endpoint namespacing.

---

## Lessons Learned

Frontend routing and backend routing should always be isolated using separate namespaces.

---

## Related Bugs

None.

# BUG-002

## Date

2026-07-24

## Version

Unknown

## Category

Backend / Spring Boot / Neo4j Domain Relationship

## Severity

High

## Status

Resolved

## Detection Method

Runtime Exception (HTTP 500 Internal Server Error)

## Symptoms

Creating a Product failed.

Error:

```text
Cannot invoke "java.util.List.add(Object)"
because the return value of
"Product.getWarrantyList()" is null
```

Automatic warranty generation failed.

---

## Immediate Cause

The application executed:

```java
product.getWarrantyList().add(warranty);
```

while `warrantyList` was `null`.

---

## Root Cause

Automatic warranty generation assumed that every Product already contained an initialized warranty collection.

Incoming Product requests no longer include a warranty list because Warranty creation is backend-managed.

---

## Investigation Summary

- Reproduced Product creation failure.
- Verified execution reached warranty generation.
- Examined stack trace.
- Confirmed warranty collection was null.
- Confirmed initialization resolved the issue.

---

## Fix Implemented

Replaced the append operation with explicit initialization.

```java
product.setWarrantyList(new ArrayList<>(List.of(warranty)));
```

---

## Files Changed

- Services/ProductService.java

---

## Verification

Verified:

- Product creation succeeds.
- Warranty generated automatically.
- Warranty relationship persisted.
- Neo4j save successful.
- No HTTP 500 errors.

---

## Regression Risk

Low

---

## Prevention

- Initialize relationship collections before mutation.
- Never assume client-created objects contain initialized collections.
- Add unit tests for automatic relationship creation.
- Add integration tests for Product creation.

---

## Lessons Learned

Backend-managed relationship collections must always be initialized before adding child entities.

---

None.

# BUG-003

## Date

2026-07-24

## Version

Unknown

## Category

Infrastructure / Spring Boot / Neo4j Connectivity

## Severity

Medium

## Status

Resolved

## Detection Method

Runtime Exception (HTTP 500 Internal Server Error)

## Symptoms

All backend operations requiring Neo4j failed.

Error:

```text
Could not open a new Neo4j session:

Unsupported authentication token,
scheme 'none' is only allowed when auth is disabled:
{ scheme='none' }
```

---

## Immediate Cause

Spring Boot failed to establish a new Neo4j session because the Neo4j driver attempted to use an invalid authentication token.

---

## Root Cause

This was a transient infrastructure/runtime issue rather than an application code defect.

The Neo4j driver or connection state became inconsistent during runtime. Restarting the backend completely reinitialized the driver and restored connectivity.

---

## Investigation Summary

- Verified failure occurred during Neo4j session creation.
- Initially suspected authentication configuration.
- Confirmed no recent authentication-related code changes.
- Restarted the Spring Boot application.
- Verified Neo4j connectivity returned immediately.
- Confirmed all APIs worked without code changes.

---

## Fix Implemented

No code modifications were required.

Resolution:

1. Stop Spring Boot.
2. Restart backend.
3. Verify Neo4j connection.

---

## Files Changed

None.

---

## Verification

Confirmed:

- Backend starts successfully.
- Neo4j sessions created normally.
- Product APIs operate correctly.
- No authentication token errors.
- Database connectivity restored.

---

## Regression Risk

Very Low

---

## Prevention

- Restart the backend before debugging sudden Neo4j authentication/session failures.
- Verify Neo4j Desktop/server is running.
- If recurring, investigate:
  - Neo4j availability
  - Driver compatibility
  - Environment variables
  - Connection pool configuration

---

## Lessons Learned

Not every HTTP 500 originates from application code. Infrastructure failures such as database connectivity or driver state can temporarily produce runtime failures that disappear after a clean restart.

# Engineering Lessons Learned

## API Design

- Separate REST APIs from frontend routing using `/api/**`.
- Avoid overlapping request mappings.

---

## Domain Modeling

- Backend-managed relationships must always initialize collections before mutation.
- Never trust incoming request objects to contain initialized collections.

---

## Infrastructure

- Verify infrastructure before assuming application defects.
- Database connectivity issues may be transient and unrelated to business logic.
- A clean application restart is often the fastest first diagnostic step for unexpected connectivity failures.
